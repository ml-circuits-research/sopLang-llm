## Introduction

The project starts from a pretrained code-capable model and changes which behavior is likely rather than installing a symbolic interpreter into the weights. Fine-tuning increases the probability of behaviors the base model can already represent: emitting SOP Lang instead of direct prose, decomposing before answering, using descriptions of available wire types, stopping neural work when a deterministic operator is appropriate, and following a structured protocol for long documents.

Model selection, teacher behavior, and runtime routing are experimental variables, so this specification records the strategy and the constraints that keep experiments comparable. Prompt and control-plane construction is specified in `DS006-context-adapter.md`, and the training recipes that consume the student are specified in `DS009-fine-tuning-and-evaluation.md`.

## Core Content

### Student size and base model

The experiment begins with the smallest pretrained model that already has enough natural-language and JavaScript competence to make specialization plausible. Training a language model from scratch would spend most of the budget rediscovering syntax, world knowledge, and coding conventions that public foundation models already provide. [A code-capable model in the sub-billion to low-billion parameter range is therefore the natural student.](wiki.html#definition-student-model)

The exact family is an experimental variable chosen from current model cards and local benchmarks when the project runs. Qwen2.5-Coder-0.5B-Instruct is an example at the scale that makes the research attractive, with a public model card reporting about 0.49 billion parameters and a 32,768-token context window. Newer models may provide better starting points, and the repository records the exact model revision rather than encoding a brand name into the methodology.

A model around half a billion parameters is an attractive lower bound because it can plausibly run at interactive rates on ordinary CPUs after quantization. A 0.8B or 1 to 2B model provides additional capacity while remaining far smaller than common agentic models, and the research trains at least two student sizes when resources permit because a scaling curve is more informative than a single checkpoint.

The smaller the model, the more important it is that the target behavior has a regular grammar and a strong external runtime. The runtime supplies capabilities that do not need to be stored as fragile neural procedures. Fine-tuning does not grant the model new reasoning capacity; it changes which of its existing behaviors dominate on SOP Lang tasks.

### Teacher models and behavioral distillation

Distillation in this project is behavioral rather than purely logit-based. A larger teacher, or more precisely an [agentic teacher system](wiki.html#definition-teacher-agent), produces decomposition decisions, circuit fragments, container schemas, and repair actions, and the student is trained on the verified trajectories. The goal is to transfer a policy for compiling problems into executable structure rather than to copy the teacher's prose.

The teacher can itself use a larger local model and can use multiple models or tool-assisted verification. The paper describes the entire teacher system because the quality of the student data depends on it: "generated by model X" is not enough when the agent also used source retrieval, code execution, unit tests, or a second judge.

The teacher's central obligation is to create executable demonstrations rather than persuasive prose. Arithmetic problems prefer solutions that generate code and verify the result, long books require source-span-grounded records with validated span boundaries, and final answers must satisfy declared schemas. The more of a demonstration that can be checked mechanically, the less synthetic-data quality depends on model self-confidence.

Teacher accuracy is a separate experimental object and student imitation is not evidence of teacher correctness. Before training, a statistically meaningful sample of accepted demonstrations is audited. Procedural problem families check the final output against the generator's oracle and, where practical, against a second independently written implementation. Document tasks use human review or designed evidence checks because no complete oracle exists, and those examples carry a confidence tier instead of being mixed silently with exact labels.

### Call-mode routing

Through the adapter, one logical request uses several bounded model calls. The `plan`, `ingest`, `compile`, `judge`, `repair`, `replan`, and `synthesize` modes described in `DS006-context-adapter.md` each carry a narrow output contract, and the grade of model used for a mode is a routing decision recorded in the run manifest.

The deployed wrapper uses the student for every mode. A larger model may be used during data generation, and an escalation baseline may be studied as an experiment in which every escalation is logged and priced separately. Hidden fallback to a larger model is prohibited because it would invalidate claims about small-model capability.

### Neural-call budgeting

The runtime counts neural calls, graph revisions, generated tokens, and wall-clock time per request. Budgets are part of the control plane and part of the request envelope, and exceeding a budget yields a structured partial result with unresolved obligations rather than a fabricated answer.

The relevant efficiency question is not tokens per second of a single call. The student is often called recursively, so prompt-processing throughput, time to first token, per-call overhead, and the distribution of call counts per task all matter. A fast single call does not imply a fast system when the policy routinely generates unnecessary recursive judgments.

Parameter count is not an efficiency metric by itself. A recursive half-billion-parameter model invoked one hundred times may use more compute than a single larger call, so evaluations report total neural tokens, total prompt tokens, call counts, accelerator time during compilation, CPU time during execution, wall-clock latency, peak memory, and compiled-state storage alongside accuracy.

### Deployment targets

The trained checkpoint is exported to the intended CPU inference format, for example GGUF when a compatible runtime is used. Quantization is evaluated rather than assumed: a checkpoint that achieves high task success in BF16 but much lower success in an aggressive 4-bit format is not reported as a high-accuracy model running at 4-bit speed. Accuracy, memory, and throughput are reported for the same exported artifact.

CPU performance is measured on named processors with fixed thread counts, prompt lengths, and output lengths. Prompt-processing throughput is separated from generation throughput, and complete task latency is measured for the whole request rather than for a single generation.

### Rationale and boundaries

The strategy separates three roles that are easy to confuse: the base model supplies language and code competence, the teacher system supplies verified trajectories, and the runtime supplies symbolic capability. The student is not expected to internalize arithmetic or bookkeeping that the runtime already performs exactly.

The strategy deliberately leaves the exact base family, teacher composition, and hardware open because they change with the available model landscape. What stays fixed is the requirement that every run records exact revisions, data exposure, and budgets, so a comparison never attributes a difference to SOP Lang when it comes from unequal training budgets or unequal model exposure.
