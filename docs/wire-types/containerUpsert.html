Wire types

containerUpsert

containerUpsert stages keyed inserts or replacements under a declared merge policy.

What it does

Use it when a record identity is known and the update may replace, merge, or preserve a competing assertion. The body names a target, an optional mergePolicy, and an items list of keyed records or a $wire reference to a computed list.

How it works

The command requires a declared identity rule, and the default reject policy rejects a conflicting replacement instead of silently selecting a winner. An explicit merge policy may permit replacement when the source record version is unchanged, merge non-conflicting fields, or create a competing assertion instead of overwriting — for information extracted from books, two passages that describe a character differently are not collapsed merely because they share an identifier. The patch is staged against the revision visible at the start of the epoch and committed with the other compatible patches at the barrier. The effect class is container_patch and the command is deterministic (version 1.1.0).

Body syntax

@resolve_characters containerUpsert
target: characters
mergePolicy: competing-assertion
items: $resolvedRecords

Worked example

A computed reconciliation that preserves competing assertions rather than picking a winner:

@resolve_characters containerUpsert
target: characters
mergePolicy: competing-assertion
items: $resolvedRecords

$resolvedRecords is a value produced by an upstream wire; the patch executes after that wire is available and still stages its update for the epoch commit. With the competing-assertion policy, a conflicting description becomes a second retained assertion instead of an overwrite.
