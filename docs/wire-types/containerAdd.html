Wire types

containerAdd

containerAdd stages one or more new records against a target container.

What it does

Use it when reading a source chunk and contributing new records to a declared container. The body names a target and an items list — either inline records or a $wire reference to a computed list. It does not replace an existing keyed record; use containerUpsert for that.

How it works

The command produces a validated container patch against the revision visible at the start of the epoch; it never mutates the target while it executes. At the epoch barrier the runtime groups patches by target container, validates conflicts, orders them deterministically, and commits one new revision — a 500-chunk book produces 500 independent additions in one revision instead of 500. The analyzer records the target as a container write and, when items is a $wire reference, that wire as a value dependency. The effect class is container_patch and the command is deterministic (version 1.1.0).

Body syntax

@chunk042_events containerAdd
target: events
items:
  - id: event_042_01
    actors: [char_hamlet]

A patch may instead depend on a computed wire:

@addNormalized containerAdd
target: observations
items: $normalizedRows

Worked example

Ingesting one event into the events sequence:

@chunk042_events containerAdd
target: events
items:
  - id: event_042_01
    actors: [char_hamlet]
    placeId: place_castle
    action: "Hamlet confronts the implication of the apparition's claim."
    temporalHint: "after the encounter"
    causes: [event_017_03]
    consequences: []
    sourceSpans:
      - { sourceId: bookA, chunkId: chunk042, start: 830, end: 1011 }

The patch stages against the revision visible now and commits at the barrier. For a sequence, every item carries an ordering key (document order, chunk order, source offset, local index) so the merged sequence is deterministic regardless of parallel completion order.
