Wire types

graphPath

graphPath answers a reachability or neighbour question over a stated undirected edge list without writing a traversal: whether a path joins two named nodes, or the degree of a named node.

What it does

The body names an edge list (edges), a start node (from), and either a target node (to) for a reachability verdict or count: true for the degree of the start node. A compiled plan never writes an adjacency map, a queue, or a seen set — the command builds the structure and runs the traversal.

How it works

The command builds the adjacency structure in edge order and runs a bounded, deterministic breadth-first search in host code. Reachability returns exactly the strings yes or no; a neighbour count returns the whole degree of the start node. The command owns the whole-number and yes/no contract.

Malformed edges, an edge list whose entries are not [a, b] pairs of comparable scalars, a start node that appears in no edge, a target node that appears in no edge, and a start equal to the target are structured execution_errors naming the wire and the contract clause. The executor is deterministic: the verdict depends only on the declared edges and nodes, never on object key ordering or runtime iteration order. The command is pure and deterministic (version 1.0.0).

Body syntax

Exactly one of to or count: true is required.

@reachable graphPath
from: $largest
to: $slots.target
edges: $slots.edges
@degree graphPath
from: $node
edges: $slots.edges
count: true

Worked example

An edge list and a reachability question, followed by a degree question:

@edges literal
[["a", "b"], ["b", "c"], ["c", "d"], ["x", "y"]]

@reachable graphPath
from: "a"
to: "d"
edges: $edges

@degree graphPath
from: "b"
edges: $edges
count: true

reachable returns "yes" because a→b→c→d is a path; degree returns 2 because b is named by the edges [a, b] and [b, c]. Changing to to "y" would return "no".
