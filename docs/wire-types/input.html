Wire types

input

input binds a value supplied by the wrapper — the current problem, a source chunk, or a runtime parameter — so a circuit reads an external value through a named wire instead of embedding it.

What it does

An input wire declares a name the wrapper fills for one request. Its body is empty and its value is immutable for the request snapshot. The runtime reads the binding from the request inputs rather than from the wire body, so the executor never runs and there is no computation to schedule.

Inputs are normally injected by the wrapper rather than invented by the student. A problem call may bind problem, sourceChunk, requestedOutputSchema, or a selected state projection. The model sees their names and contracts in the control plane, which keeps the boundary between data and executable code explicit and prevents a generated circuit from smuggling source text into program syntax.

How it works

The analyzer reports no value dependencies: the wire reads from the request inputs, not from another wire. The validator requires the body to be empty; any non-whitespace body is a validation_error. The executor returns undefined because the binding is read by the runtime, never produced by the body. The command is pure and deterministic (version 1.0.0).

A binding whose name has no declared wire becomes an implicit input node, so the circuit does not need a separate declaration to read a wrapper-supplied value.

Body syntax

The body is empty. The wire name is the binding name.

@problem input

Worked example

A circuit that counts the words in the injected problem and publishes the count:

@problem input

@wordCount jsEval
return $problem.trim().split(/\s+/).length;

@answer jsEval
return { count: $wordCount };

The wrapper supplies problem; wordCount reads it as a $wire dependency, and answer publishes the result. Nothing in the circuit embeds the problem text — it arrives as data.
