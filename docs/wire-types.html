Wire types

Every capability the runtime offers is a wire command. A small standard vocabulary gives the student stable concepts, and installable wire types add capability that the model composes from descriptions instead of memorizing.

Standard vocabulary

CommandPurposeState and effect model
inputBind a value supplied by the wrapper, such as the current problem, chunk, or runtime parameter.Immutable for one request or declared snapshot.
literalProduce a literal scalar, JSON value, or text body.Pure.
jsEvalExecute JavaScript over declared $wire dependencies in an isolated realm, and optionally stage graph or container transactions.Pure unless it explicitly stages effects; bounded by the JavaScript deadline.
modelCallInvoke the configured neural model for a local semantic judgment or generation step.Explicit non-deterministic neural effect, fully logged.
containerDeclare a typed persistent collection with its schema and identity policy.Structural state declaration.
containerAddStage one or more new records for a target container.Batched container patch.
containerUpsertStage keyed inserts or replacements under a declared merge policy.Batched container patch.
containerRemoveStage deletion or tombstone operations under an explicit identity contract.Batched container patch.
containerFilterDefine a pure derived view of a source container that keeps provenance.Pure, and invalidated when source or predicate dependencies change.

Input wires are normally injected by the wrapper rather than invented by the student. A problem call may bind problem, sourceChunk, requestedOutputSchema, or a selected state projection, and the model sees their names and contracts in the control plane. Large source documents are not embedded as literal values inside generated programs; they stay in a source store and are referenced by input wires or source identifiers, which keeps provenance stable.

The deterministic escape hatch

jsEval supports ordinary JavaScript data structures and small algorithms, and the student is trained to prefer it whenever the remaining problem is mechanical: sorting records by timestamp, computing a median, joining rows by identifier, finding connected components, validating a JSON object, or serializing an answer. A body runs in an isolated guest realm inside a worker thread: dependency values arrive as copies through the value profile, generated code cannot reach the host process or the module system, and the circuit parameter is a facade whose operations are replayed onto the real transaction after the call. Execution is bounded, so a nonterminating body ends as a structured budget_exceeded outcome, and consumed JavaScript time is charged cumulatively. The research semantics do not depend on pretending JavaScript is less expressive than it is, and they also do not depend on a deployment sandbox: the isolation makes a generated program unable to mutate runtime state outside its declared effects.

Explicit neural work

modelCall makes recursive neural reasoning visible. A wire body contains the local instruction, the relevant dependency values, and an optional constrained output schema. A summarization circuit may use model calls for claim extraction or paraphrase while accounting for coverage in JavaScript, and a novelty circuit may use retrieval and deterministic overlap metrics first and a neural judge only on the remaining candidate comparisons. Every invocation is a visible cost center that can be ablated.

Wire type modules

An additional command is implemented by an ECMAScript module that exports a wireType object with three layers: a manifest that may be shown to the model, an analyzer and validator used by the compiler, and an executor used by the runtime. The relative module path may determine the command name: a file at wires/text/paraphrase.mjs can expose text.paraphrase, and a file placed directly at wires/paraphrase.mjs exposes paraphrase.

export const wireType = {
  manifest: {
    name: "text.paraphrase",
    version: "1.0.0",
    summary: "Rewrite supplied text while preserving specified facts and constraints.",
    whenToUse: "Use when wording must change but semantic content is already known.",
    whenNotToUse: "Do not use to discover facts or perform arithmetic.",
    bodyFormat: "text",
    syntax: "@out text.paraphrase\n$input\n<rewrite instruction>",
    inputContract: {
      requiredDependencies: ["text-like value"],
      notes: "All referenced values must appear as $wire dependencies."
    },
    outputSchema: { "type": "string" },
    effectClass: "neural",
    determinism: "not_guaranteed",
    examples: [
      {
        source: "@short text.paraphrase\n$draft\nMake this concise without dropping qualifications.",
        explanation: "Uses an existing draft as the value dependency."
      }
    ]
  },

  analyze({ body, parser }) {
    return parser.findValueReferences(body);
  },

  validate({ body, capabilities }) {
    return { ok: true };
  },

  async execute(ctx) {
    return ctx.models.paraphrase({
      body: ctx.body,
      values: ctx.values,
      budget: ctx.budget
    });
  }
};

The three layers

The manifest is part of the capability catalog presented to the planner, not documentation for humans alone. It states the command name and version, purpose, when to use it and when not to, the accepted body form, how dependencies are referenced, the output contract, the effect class, determinism, and canonical examples. A vague description such as "processes text intelligently" is unacceptable because the student cannot make a reliable planning decision from it.

The analyzer is equally important. Scheduling is sound only when the runtime knows which values are required before execution, so a command never inspects runtime values to discover dependencies after execution has begun. The body language decides the lexical rule: JavaScript analysis ignores string literals, comments, regular-expression literals, and property names, while instruction text has no string literals and therefore reads a $name token wherever it appears, so an apostrophe in What's $x? never hides a required input. Dynamic dependency creation belongs to metaprogramming and a new circuit revision.

The validator checks body syntax and static constraints before execution. A validation error is a compilation failure, not a natural-language warning. The executor receives immutable resolved dependency values, the original body, declared budgets, versioned resources, and only the runtime APIs permitted by its effect class, which prevents the scheduler from assuming that two commands are parallel-safe merely because their current data dependencies do not intersect. A declared data contract is validated fail-closed: a schema outside the published profile is rejected as unsupported_schema before any record or output is accepted.

Versioning and conformance

The manifest and the executable code are versioned together, and the trace records the implementation hash. If a description says that a command sorts ascending while the code sorts descending, the experiment is invalid regardless of how well the student follows the description. Automated conformance tests generate sample inputs from the declared schema and check the relationships the manifest claims.

Training exposes the student to varying capability catalogs. Some examples rename semantically equivalent tools with random identifiers and provide only the manifest, and other examples withhold a wire type entirely until evaluation. Success on unseen commands shows that the model interprets tool descriptions and composes them rather than memorizing SOP Lang token sequences.

Where the contract lives

The vocabulary, the module contract, and the conformance requirements are specified in DS004-wire-types. Container commands are specified in detail in DS005-containers, and the scheduling and transaction rules that all commands obey are specified in DS002-sop-lang-core.
