Teaching

Teaching pipeline

A teacher agent produces the verified trajectories that train the student. It does not invent examples in bulk. It builds problem families with generators, renderers, oracles, validators, and difficulty schedules, and the pipeline decides what enters the dataset.

The teacher is an agentic production system

A coding agent is a natural teacher for this project because the target behavior is executable. It can inspect a problem, design a decomposition, write SOP Lang, implement or call wire types, execute the circuit, create tests, compare outputs with an oracle, diagnose failures, and revise the solution. A static language model asked for one ideal answer cannot close that loop as reliably.

The design choice is not to trust the coding agent because it is sophisticated. It is trusted only when its artifacts pass independent checks. The teacher proposes, and the data factory decides what is accepted. A typical teaching episode starts from a problem specification whose answer can be checked independently. The agent decides whether to decompose further, produces a circuit, runs it, and compares the output with the oracle. A wrong result is repaired from the trace, and both the final accepted trajectory and selected failure and repair pairs are preserved because deployed systems also replan after execution errors.

Problem factories

The weakest way to create synthetic data is to ask a coding agent to invent a hundred thousand diverse reasoning problems, which produces repeated surface forms, uneven difficulty, invisible gaps, and tasks without independent answers. The stronger approach treats dataset generation as software engineering.

Every family has a specification with the latent structure of the task, a generator, a natural-language renderer, an oracle, mutation operators, a difficulty vector, and coverage labels. A table-reasoning generator may sample a relational pipeline such as filtering by predicate, joining two keyed tables, grouping by a field, computing an aggregate, selecting the top k, and rendering the result. The natural-language question is produced from that latent plan, and the oracle executes the plan independently. The teacher sees the question and the available wire types, not the hidden oracle program.

Difficulty is multidimensional. Useful dimensions include the number of subproblems, dependency depth, branching factor, irrelevant information, available but unnecessary wire types, recursion, container revisions, ambiguity requiring additional context, intermediate data size, and the fraction of work that can be delegated symbolically.

The factory includes template mutation rather than superficial paraphrase: it permutes operation order where semantics permit, renames entities, changes units, introduces decoy tools, moves critical evidence, alters container schemas, and replaces familiar command names with random ones. These transformations test structural generalization instead of linguistic memorization.

Seed environments

The books in vision/ are seed environments. They are not fed into fine-tuning as raw next-token data, which would risk memorization and would not teach compiler behavior. The teacher reads a source, constructs candidate semantic inventories, and creates tasks whose answers must be grounded in the source.

Dataset layout and text artifacts

The dataset is a tree of text files under training-data/. Two main sets separate examples by the knowledge they need: no-knowledge/ holds problems whose solution is fully stated by the problem text, and knowledge/ holds problems whose solution needs an external fact, such as a unit convention, a calendar fact, a currency, or a formula that the text does not state. A knowledge-requiring problem is filed under knowledge/ rather than discarded, and its circuit materializes the fact as a structured facts literal wire that the computation reads: the writer removes the wire and re-runs the circuit, so a fact the program does not actually read is rejected as fact_not_load_bearing, and a substring guard on the fact text is rejected at load time. Inside a category, the next level is the problem type, which is the printed template reduced to a slug, so a large dataset stays navigable and a coverage report can count latent plans directly.

Every problem folder holds exactly three files. problem.md is the statement and nothing else, plus a labelled Referenced context line when the statement hands its premise to an earlier problem, because it is the solver-visible projection. solution.sop is the SOP Lang circuit and the compiled plan of that instance: a slots literal wire carries the values the compiling model extracted from the statement, an optional facts literal wire carries external knowledge, and the answer wire performs the deterministic jsEval computation. Dataset circuits contain no input wire and no modelCall wire, because the SOP Lang file is itself the model's output: an input wire would only re-state data the plan carries, and a model call would ask a model to re-parse its own input. explanation.md has two sections, ## Explanation for the reasoning steps with the reference solution printed by the source, and ## Result for the answer, the acceptance class, and the program file.

One percent of the accepted examples form the evaluation holdout under eval/, selected deterministically from a hash ordering, stratified by category, and taken in whole template clusters merged by shared plan fingerprint (the facts and compute body of the circuit) so neither the variants of one template nor a near-identical plan straddle the split. An eval example is excluded from the training sets by construction. Candidates that were extracted but not accepted are preserved under rejected/ with the reason, because coverage is measured by counting them rather than by an impression. Text manifests and reports lock the dataset: sources.md records role, rights, raw and canonical hashes, and the extractor profile, manifest.md carries one row per accepted example with its hashes and split, and report.md states counts, rejection reasons, distinct plans, and limitations.

Problem families and verification

A problem family turns one printed template into a verified example. It carries the reference parse that the compiling model performs when it reads the statement, an independent computation over the parsed values, the answer text the source prints, the SOP Lang computation body, and the explanation steps. The family is written against the statement only: it never reads the printed answer or the abstract model of the source.

Acceptance is a three-way agreement. The circuit is executed by the runtime with the instance's parsed values materialized as the slots literal, and the executed answer must equal both the printed answer and the independent computation of the family; only then is the example exact_verified. The circuit compute bodies keep the validity guards of their family solve and their jsEval stage always carries the probe harness, so a circuit neither returns a value the oracle would reject nor publishes an empty answer, and a malformed input ends the run as a structured execution_error. The family solve and the circuit compute are two transcriptions of one algorithm over one shared parse, so the dataset report states that independence limitation. The loader rejects a family whose program declares an input or modelCall wire or whose answer wire lacks the probe harness, and the writer's English-only gate scans every generated file before the manifest is locked. Because the variants of a template compile to distinct circuit text — a compiled circuit embeds its instance values — the plan fingerprint (facts and compute body) is the latent-plan identity, and the report counts distinct plans next to the accepted examples, with the writer asserting that no eval plan appears in the training rows.

Coverage matrix and acceptance

The dataset needs a competence matrix before large-scale generation begins. The first axis describes the role of the student call: initial decomposition, circuit planning, chunk ingestion, local semantic judgment, repair, replanning, final synthesis, schema planning, or tool selection. The second axis describes task families: numerical, algorithmic, tabular, document, legal, literary, scientific, debugging, retrieval, summarization, anti-smoothing, novelty, and mixed tool workflows. The third axis captures the difficulty dimensions.

The factory tracks how many accepted examples occupy each cell and also tracks failure rate, average circuit size, average neural-call count, and symbolic delegation. If almost every example uses jsEval only for arithmetic and almost none require graph expansion, the student will not learn recursive planning regardless of total dataset size.

Before an example enters the training set it passes syntax parsing, command validation, dependency analysis, acyclicity checks for the generated revision, execution where applicable, oracle comparison, schema checks, provenance checks, and leakage checks. Each accepted example carries an acceptance class: exact_verified, computed_verified, execution_verified, evidence_verified, or human_audited. An example whose source prints one of several valid answers, or a value that contradicts its own stated numbers, ships the computed answer under computed_verified: the family declares the status, a predicate confirms the printed answer from the statement's own data, and the printed answer stays in explanation.md as reference material.

Leakage and rights

Document-level splitting happens before task generation. When a book contributes training examples, no chapter or paraphrased derivative from that book appears in the final held-out book evaluation unless the evaluation is explicitly about within-book adaptation. Evaluation problem generators and held-out sources are stored behind a separate interface, and the agent that creates the training set has no access to test seeds or hidden test manifests.

Copyright and licensing are respected. Sources the project owns or may use internally can serve as private training material, while redistributed datasets may contain only derived annotations or generated synthetic substitutes. The experiment manifest records the rights status of each source and whether it may appear in released artifacts.
