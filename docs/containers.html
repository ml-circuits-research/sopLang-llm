Containers

Long-document reasoning needs state that is more structured than a list of chunks and less brittle than a succession of prose summaries. A container is a typed persistent collection declared as a first-class wire value with an explicit schema, identity policy, provenance, and revision semantics.

Collection kinds

The reference profile supports three collection semantics. A table is a collection of JSON-like records governed by a record schema and, optionally, primary or candidate keys. A set is a collection whose membership is defined by a stable identity function or canonical hash. A sequence is an ordered collection whose order is meaningful, such as a chronology of events or the order of passages in a narrative. Graph relations are ordinary tables whose fields act as foreign keys, which keeps storage and validation simple while allowing graph algorithms in JavaScript.

A planning call for a novel may declare containers before any source chunk is read:

@characters container
kind: table
primaryKey: id
schema:
  type: object
  required: [id, name, sourceSpans]
  properties:
    id: { type: string }
    name: { type: string }
    aliases: { type: array, items: { type: string } }
    traits: { type: array, items: { type: string } }
    sourceSpans: { type: array }

@events container
kind: sequence
schema:
  type: object
  required: [id, actors, action, sourceSpans]
  properties:
    id: { type: string }
    actors: { type: array, items: { type: string } }
    placeId: { type: [string, "null"] }
    action: { type: string }
    temporalHint: { type: [string, "null"] }
    causes: { type: array, items: { type: string } }
    consequences: { type: array, items: { type: string } }
    sourceSpans: { type: array }

After the planning call these definitions become part of the trusted runtime state supplied to ingestion calls. The source chunk remains data, and the schema is a system capability and contract.

Patch-based updates

A naive implementation would turn every appended record into a graph rewrite and restart the scheduler constantly. Container mutation commands avoid that by not mutating the target while they execute. containerAdd, containerUpsert, and containerRemove produce validated container patches against the revision visible at the start of the epoch, and compatible patches that become ready during the epoch are computed in parallel.

@chunk042_events containerAdd
target: events
items:
  - id: event_042_01
    actors: [char_hamlet]
    placeId: place_castle
    action: "Hamlet confronts the implication of the apparition's claim."
    temporalHint: "after the encounter"
    causes: [event_017_03]
    consequences: []
    sourceSpans:
      - { sourceId: bookA, chunkId: chunk042, start: 830, end: 1011 }

A patch may instead depend on a computed wire, in which case it executes after that wire is available and still stages its update for the epoch commit:

@normalizedRows jsEval
return $rawRows.map(normalizeRow);

@addNormalized containerAdd
target: observations
items: $normalizedRows

At the barrier the runtime groups patches by target container, validates conflicts, orders them deterministically, and commits one new revision. A 500-chunk book produces 500 independent additions that commit in one revision instead of 500. For a sequence, completion order must not define semantic order because parallel scheduling would make it nondeterministic, so every item carries an ordering key such as source document order, chunk order, source offset, and local index, and the merged sequence is sorted by that key.

Identity, merge policy, and history

containerUpsert requires a declared identity rule, and the default rejects a conflicting replacement instead of silently selecting a winner. An explicit merge policy may permit replacement when the source record version is unchanged, merging non-conflicting fields, or creating a competing assertion instead of overwriting. For information extracted from books, preserving competing assertions is often preferable: two passages that describe a character differently are not collapsed merely because they share an identifier. containerRemove normally creates a tombstone or a new revision rather than erasing history, so replay and audit remain possible. Every accepted item is also recorded in an append-only history with the record it replaced, so an earlier assertion and its source spans stay retrievable by revision after a replacement or a merge, while the canonical view may change. A patch that the store rejects as part of a group publishes nothing: each group is applied to a working copy and replaces the live state only when the whole group is accepted, and a set is defined by membership identity, so a repeated member never inflates a downstream count.

Derived views and invalidation

containerFilter defines a pure derived view of a source container. Its value depends on the source container revision and on any additional predicate dependencies, and it preserves provenance by referencing source record identities and the revision it was computed from.

@highConfidenceClaims containerFilter
source: $claims
predicate:
  return row.confidence >= $threshold && row.status !== "superseded";

When either the source container or the threshold changes, the view becomes dirty and downstream wires become dirty transitively. The rule holds through composition: a correction that adds a previously missed legal exception creates a new base revision, invalidates the filter that selects exceptions by date, and invalidates the JavaScript wire that groups them by jurisdiction. Incremental maintenance is allowed as an optimization only when it produces the same result and trace-equivalent provenance.

Interaction with metaprogramming

A jsEval wire may decide that a new container or view is required and define it through the circuit API. That is a structural transaction and produces a new circuit revision. Ordinary additions use container patches and are batched within the current epoch. The distinction gives the student a clear planning rule: container mutation commands handle data, and the circuit API handles changes to computational structure.

Containers as evaluation substrate

Containers support controlled summarization and anti-smoothing measurement. The system compiles claims, exceptions, events, positions, and evidence into containers, marks which records are mandatory for the requested summary policy, generates prose, and measures coverage against those records. The container state serves as working memory and as evaluation substrate at the same time.

Where the contract lives

The full container contract, including patch records, merge policies, tombstones, and invalidation rules, is specified in DS005-containers. The epoch semantics that make batched commits possible are specified in DS002-sop-lang-core, and the planning and ingestion flow that fills containers is specified in DS006-context-adapter.
