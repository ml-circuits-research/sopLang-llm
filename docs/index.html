sopLang-llm

sopLang-llm fine-tunes a small code-capable language model to compile a problem into an executable SOP Lang circuit instead of generating the final answer directly. A runtime resolves the circuit's dependencies, runs JavaScript for deterministic work, invokes declared tools or bounded neural judgments where semantics remain necessary, and publishes a result that traces back to the circuit that produced it.

How the system fits together

The project separates three responsibilities that most language-model systems collapse into one autoregressive response. The student model interprets the task, decomposes it, selects capabilities, and emits a circuit. The runtime schedules and executes that circuit with exact computation, typed state, and explicit modelCall nodes. The data factory builds verified teaching material, and the fine-tuning laboratory turns that material into the student.

The model is deliberately relieved of arithmetic, bookkeeping, formatting, filtering, aggregation, and classical algorithmic work. Its learned behavior of interest is symbolic delegation: recognizing when a subproblem has become mechanical enough that further neural reasoning should stop.

Coding style and tests

The canonical source for coding style, source layout, and test organization is DS001-coding-style. Executable code is Node.js ECMAScript modules in .mjs files with built-ins only, and tests use node --test with node:assert/strict. The required coverage per contract surface is listed in the specification.

Implementation status

The repository currently ships the language runtime under runtime/ and the standard vocabulary under wires/standard/, with a test suite that covers the parser, dependency analysis, scheduling, epochs and revisions, containers, metaprogramming, tracing and replay, the registry and profile readers, the schema profile, the isolated JavaScript sandbox, and compiled-context end-to-end scenarios.

The executable language implementation is complete for the standard vocabulary and is covered by that exercised behavior. The data pipeline is implemented for all seven seed books: context/sources/docx.mjs extracts a seed book with the versioned canonical profile, teacher/families/ holds the problem families of the seed books, and teacher/pilot.mjs compiles and verifies book-derived examples into training-data/ under the layout of DS008-training-data. A dataset circuit is the compiled plan of one instance: a slots literal wire carries the values extracted from the statement, an optional facts literal carries external knowledge, and the answer wire performs the deterministic jsEval computation; dataset circuits contain no input wire and no modelCall wire, because the SOP Lang file is itself the compiling model's output. All seven seed books are compiled, 1000 accepted examples each, with 7000 accepted examples across the suite, 1061 covered templates, 893 distinct plan fingerprints, and 225 held-out evaluation examples (10 to 100 per book, clustered by shared plan fingerprint so no evaluation plan occurs in a training row). No candidate stays rejected: an example whose printed answer the statement does not determine is recovered through a declared clarification sentence, a computed answer with a printed-answer status verified against the source, or a source-level answer normalization, and every recovery is recorded in the book's manifest rows. Each book names its unit of work (a chapter, a section, a reasoning family, a template, a form, or a pattern) and carries per-unit manifests with content hashes and plan fingerprints. Every dataset circuit also carries the probe harness inside its jsEval stage, and the independent verifier re-checks the shipped trees for the harness, for ambiguous statements, and for answers that do not react to their inputs. The installable wire loader under wires/custom/, templates under wires/templates/, the remaining context adapter machinery, the learning-based teacher, and the benchmark suites under benchmarks/ are planned work described by their specifications. Statements about those surfaces are specifications of intended behavior, not reports of exercised behavior.

The fine-tuning laboratory and the evaluation loop are implemented and measured on that dataset. training/export.mjs derives the trainer view (6775 rows, chat profile compiled-plan-chat-1), training/python/sft_train.py trains on the pinned Qwen2.5-Coder-0.5B-Instruct revision with a declared device-memory budget, and evaluation/ holds the serving client, the evaluation loop, checkpoint selection, the capability probes, and the evidence registry. The first series is complete for three arms: the untuned base answers 0 of 50 sampled holdout problems directly and parses none of its zero-shot emissions, the tiny overfit gate passes all three of its gates, and the two full runs (learning rates 2e-5 and 1e-4, 606 steps each) reach 53.7% and 94.7% oracle match on the plan-aware validation slice against 0.0% on the 225-item plan-disjoint holdout. The failure analysis records why: rows on a plan fingerprint the trainer saw score 98.8%, rows on an unseen plan 12.5%, and rows from families absent from the export 0%, with 80 of 225 completions splicing two memorized program bodies and 77 compiling the wrong inputs. The measured limitation is plan coverage, so the next series widens the family set of the training books before changing student size or recipe. The LoRA arm of the same series is running.

Design specifications

The design specifications under docs/specs/ are the source of truth for documented behavior and structure. When prose elsewhere diverges from a specification, the specification wins. The set begins with the vision, the coding style, and the language contract, then defines the main behaviors, the wire vocabulary, container semantics, the context adapter, the model strategy, the training data suite, and the evaluation methodology.

Evidence discipline

Every training and evaluation run is driven by a machine-readable manifest that records model and tokenizer revisions, dataset hashes, split identifiers, random seeds, and runtime configuration. Per-item records are written before aggregate statistics, and reported tables are generated from those records. A result that cannot be traced back to a raw record does not appear in a report, and the evidence registry keeps negative results so they influence the interpretation of the work.
