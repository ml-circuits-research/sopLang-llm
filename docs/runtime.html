Execution

Runtime

The runtime turns a circuit into a result that can be defended. It extracts dependencies, rejects cycles, computes a deterministic schedule, evaluates wires in epochs over immutable snapshots, commits staged effects at epoch boundaries, and publishes only a validated output wire together with a trace.

Scheduling

For a fixed graph revision the runtime computes the active dependency closure from the requested output wires and any configured control roots, then performs a deterministic topological sort. Kahn's algorithm is the reference implementation: compute the in-degree of every active node, repeatedly select zero-in-degree nodes in a stable lexical or creation order, emit them, and decrement their successors. If active nodes remain when no zero-in-degree node exists, the circuit contains a cycle and execution fails before any final answer is published.

The reference implementation may execute all ready wires serially while preserving epoch semantics, and parallel execution is enabled later for wire types declared safe. Correctness takes precedence over throughput because the research depends on trustworthy traces.

Epochs and commits

An epoch is the evaluation of a stable graph and state snapshot. Wires observe immutable dependency values from that snapshot, pure wires may run in parallel once their dependencies are satisfied, and effect-producing wires stage validated effects instead of mutating shared state immediately. At the epoch barrier the runtime groups container patches by target container, validates conflicts, orders them deterministically, and commits one new container revision. Structural graph transactions commit in the same barrier.

Revisions and invalidation

A restart is a move from one immutable snapshot to another, not a jump backward in execution. Cached values are reused only when their definition hashes, dependency revisions, command implementation versions, and external resource versions remain compatible. A redefinition of a wire invalidates that wire and all downstream value consumers. An update to a container invalidates materialized views and any wire that depended on the old revision. A graph mutation that does not touch a pure subgraph does not force recomputation of that subgraph.

Every structural change advances the circuit revision counter, so two same-size revisions stay distinguishable. A read of a container is recognized both when it is declared, as in the source of a containerFilter, and when it is an ordinary value read such as $claims in a jsEval body or a model instruction; both activate the contributions of the writers and the invalidation of the readers. A composed chain such as base container, first filter, second filter, and the scalar computed from it is invalidated link by link from the base commit.

Explicit invalidation follows the same reach. circuit.invalidateWire marks the named wire and every affected consumer, including transitive dependencies, because a refreshed observation must reach the output that depends on it; circuit.invalidateDownstream marks the consumers without invalidating the named wire. A wire that read a definition through circuit.getDefinition or listed names through circuit.listDefinitions is a structural consumer and is invalidated when an observed definition changes or when the set of names matching a listed prefix changes.

Structural invalidation is separate from semantic correction. When reconciliation concludes that two extracted identifiers refer to the same entity, the container state changes and downstream views are invalidated, but historical provenance is not rewritten: the original record and its source span stay in the audit log, and a canonical view merges them.

Isolated JavaScript

Generated code runs in a private guest realm inside a worker thread. The realm contains only ECMAScript intrinsics, so a body cannot reach the host process, the module system, or any runtime object. Dependency values and container snapshots cross the value profile as copies, so a mutation inside a body never reaches a caller value, a sibling observation, a stored record, or a container revision; persistent change requires a committed patch and a new revision. The circuit parameter is a guest-realm facade whose operations and structural reads are replayed onto the real transaction after the call, and an uncommitted transaction publishes nothing. Container filter predicates run in the same isolated realm.

Execution is bounded twice. The synchronous part of a call runs under the realm's script timeout, and the worker is terminated when the call exceeds its JavaScript deadline, so a nonterminating body ends as a structured budget_exceeded outcome instead of blocking the runtime. Consumed JavaScript time is charged cumulatively against the request budget.

Tracing and replay

A trace records at least the circuit revision, epoch number, wire name, command identity and version, definition hash, dependency identities, execution start and end, output hash, staged effects, transaction details, neural-call metadata where relevant, replay provenance, and any error. A dependency identity names the dependency, its definition hash, and the hash of the value that was observed, so a record identifies the exact graph-and-state snapshot it belongs to. A rejected wire is recorded with the same identity fields as a successful one, and a failed run keeps the trace of the wires that completed before it.

For neural wires, exact replay and fresh rerun are distinguished. Exact replay substitutes a recorded response only when the definition hash and the dependency value hashes match; a mismatch is rejected as replay_mismatch rather than returning a stale answer, and the substitution is recorded with the provenance of the entry it replayed. A rerun invokes the model again and may produce a different result even with nominally deterministic decoding, so the project does not claim bit-for-bit reproducibility of neural generation.

Budgets and structured outcomes

The runtime caps the number of epochs, total created wires, neural calls, JavaScript time, output bytes, and transaction operations. Exceeding a budget yields a structured budget_exceeded result with a trace of partial progress rather than an invented answer. The same principle covers unresolved dependencies, cycle detection, schema failure, and tool errors: they produce structured partial or failed outcomes. A malformed program is normalized into a failed outcome with a stable parse_error code and an error record instead of rejecting the call, so a dataset worker rejects one candidate without aborting its batch.

Normative runtime contract

The normative implementation state contains a versioned circuit definition, a dependency graph, a value store, a command registry, container revisions, an effect staging area, a transaction log, and explicit resource budgets. A wire has a name, command identity and version, body, normalized definition hash, value dependencies, structural dependencies, metadata, and evaluation state. Valid states include at least pending, ready, running, valid, dirty, failed, and cancelled.

The API available to jsEval exposes graph mutation but no hidden value store. circuit.getDefinition returns the actual definition of the current revision and circuit.listDefinitions returns the definitions matching a prefix, while circuit.getValue does not exist, so values enter through declared $wire dependencies. A transaction records transactionId, parentRevision, originWire, the structural read set, the write set, operations, and an intent hash. Replaying the same intent against the same parent revision returns the same commit result without repeating its effects, re-adding a name whose definition is unchanged is an idempotent no-op, reusing an identifier with different content is a conflict, and a wire that stages operations without calling circuit.commit publishes nothing.

Running a circuit

The library entry point is runtime/kernel.mjs. A request supplies input bindings, the output wires to produce, optional model bindings for modelCall, optional budgets, an optional output schema, an optional existing container store, and the run mode.

import { createRuntime } from './runtime/kernel.mjs';

const runtime = createRuntime();
const result = await runtime.run(source, {
  inputs: { rows: [{ enabled: true, amount: 4 }] },
  outputs: ['output'],
  models: { modelCall: async ({ instruction, values }) => judge(instruction, values) },
  budget: { maxNeuralCalls: 4 },
  outputSchema: { type: 'object', required: ['answer'] }
});

console.log(result.status);   // completed
console.log(result.outputs);  // requested wire values
console.log(result.trace);    // per-wire hashes, dependencies, and output hashes

A run status reports one of three outcomes. completed carries the requested output values. partial reports a budget limit or an unresolved dependency together with the partial output and trace. failed reports a parse, validation, execution, or cycle error with a stable code such as parse_error, unknown_command, unknown_output, unknown_dependency, cycle_detected, validation_error, missing_input, stale_definition, effect_not_permitted, execution_error, unsupported_schema, unsupported_value, replay_mismatch, or budget_exceeded, and partial reports unresolved_dependencies when a producer never appears.

Replay

Running the same circuit in replay mode with a recorded trace substitutes each recorded neural generation instead of invoking the model again. The downstream deterministic computation then runs over the recorded text, which is how a reviewer verifies that a reported answer follows from the recorded generation.

const live = await runtime.run(source, { inputs, models });
const replayed = await runtime.run(source, { inputs, mode: 'replay', replayFrom: live.trace });
