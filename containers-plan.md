# Container plans: what exists, what blocks, and the six steps

This document is the read-only plan for wiring the container and registry-reading shapes of `DS008-training-data.md` into the data pipeline. It records what the runtime already provides, what the four coupled gates of the D-G decision block, why the book families' 40-to-67-line `jsEval` bodies are the symptom those shapes are meant to cure, and a six-step plan ordered by dependency. Nothing here is implemented; the only write is this file, and every file named below is read-only for the author of this plan.

## What exists: the five container commands

The runtime ships exactly five container commands, all version 1.1.0, exported as `containerCommands` from `wires/standard/containers.mjs`. They are not value-producing computation in the `jsEval` sense; they are trusted runtime state and staged patches over it. Their contracts, taken from the module's header and per-command `manifest`/`analyze`:

| command | effect class | body (profile) | what it does | what `analyze` reports |
| --- | --- | --- | --- | --- |
| `container` | `pure` | `kind`, `primaryKey`, `identity`, `schema`, `mergePolicy` | declares a typed persistent collection; the schema and identity policy become trusted runtime state; the wire's value is the container snapshot, and a commit invalidates the declaration wire so the next epoch returns the new revision | `containerReads: [wire]`, no writes |
| `containerAdd` | `container_patch` | `target`, `items` (may be a `$wire` reference) | stages one or more new records against the target container | `values` from a `$items` reference, `containerWrites: [target]` |
| `containerUpsert` | `container_patch` | `target`, `mergePolicy`, `items` | stages keyed inserts or replacements under a declared merge policy | `containerWrites: [target]` |
| `containerRemove` | `container_patch` | `target`, `items` | stages deletion/tombstone under an explicit identity contract; history stays auditable | `containerWrites: [target]` |
| `containerFilter` | `pure` | `source: $container`, `predicate` (JavaScript over a `row`) | defines a pure derived view of a source container, retaining provenance (`viewOf`); filters compose because a filter may read another view | `values` from predicate references (excluding `row`), `containerReads: [source]` |

The governing contract is in the header comment: a declaration is a structural state declaration whose schema and identity policy become trusted runtime state; the mutation commands stage patches against the revision visible at the start of the epoch; the store commits compatible patches together, increments the revision once per grouped commit, and invalidates the wires that read the container. A `containerFilter` keeps the source revision through a filter chain, so provenance stays traceable and every link of the chain is invalidated by the base commit. The runtime's dependency graph (`runtime/graph.mjs`) already recognizes a container read both when a wire declares the container and when a later wire reads it (`source` of a filter, or a `$name` value read), and it propagates invalidation from writers to readers. So the runtime half of the container shape is complete; what is missing is entirely on the teacher/verifier side, which is exactly what the D-G decision found.

## What the four gates block

D-G in `evaluation/registry/phase4-analysis.md` names four coupled gates, and each one is still present in the code as of this reading.

**Gate 1 — the family validator accepts only five intermediate-wire commands.** `validateProceduralFamily` in `teacher/procedural/index.mjs` rejects any intermediate wire whose `command` is not in the literal whitelist `["jsEval", "literal", "graphPath", "aggregate", "fraction"]`. D-G wrote "jsEval and literal" because that is what the whitelist held on the night it was recorded; the declarative commands `graphPath`/`aggregate`/`fraction` have since joined it, but the five container commands have not. A procedural family that declares `container`, `containerAdd`, `containerUpsert`, `containerRemove`, or `containerFilter` as an intermediate wire therefore fails at load time, before any file is written. This is the first hard block: no procedural source can declare a container plan.

**Gate 2 — the program builder has no container path.** `buildProgram` in `teacher/families/index.mjs` assembles every dataset circuit (book and procedural alike, since `teacher/pilot.mjs` calls the same `buildProgram` for both): an optional `facts` literal, the `slots` literal, the `entry.wires` intermediate wires, and a final `answer` `jsEval`. Its intermediate-wire loop is generic — it emits `@name command` and applies `answerBody` only when the command is `jsEval`, passing any other body through as `String(wire.body)` — so a container profile body would in principle flow through verbatim. But there is no container-specific path behind that generic loop: nothing guarantees the `container` declaration precedes the mutations and filters that name it, nothing validates a container profile body at build time, and nothing proves the built circuit round-trips through the runtime. The loop happens to be permissive; the builder does not know containers exist, and there is no acceptance test that would catch a container circuit that the parser or the runtime then rejects. `validateCase` (the book-side validator in the same file) parses `buildProgram(entry, {})` and asserts the `answer` wire is `jsEval` and that no `input`/`modelCall` wire appears, but it asserts nothing about container bodies or their ordering.

**Gate 3 — the provenance battery cannot see container reactivity.** `verifyProvenance` in `training-data/provenance.mjs` proves an answer is a function of its inputs by perturbing the `slots` literal (`perturbedSlotBodies` / `withSlotsBody`) and requiring the answer to change. Two things break for a container plan. First, the perturbation only reaches container contents if the container is seeded from a `$slots` or `$facts` reference — a `containerAdd items: $slots.records` — because `withSlotsBody` swaps only the `slots` wire; a seed that is a baked intermediate `literal` would not react and the plan would be flagged as non-reacting even though the family computed it. Second, the diagnostic that classifies a non-reacting circuit scans `findValueReferences(stripProbeStatements(wire.body))`, a JavaScript reference analyzer, which does not understand the `target`/`items`/`source`/predicate fields of a container profile body, so it would report a reactive, seeded container plan as `usesInputs: false`. The functional perturbation run goes through the runtime and would work if the seed is a `$slots` reference, but the classification and the seeding discipline are both absent.

**Gate 4 — no manifest column records the structural read set.** `DS008-training-data.md` requires a registry-reading plan's manifest row to record the structural read set, the definition names its body reads through `circuit.getDefinition` or `circuit.listDefinitions`, because a wire that observed a definition is invalidated when that definition changes. The shipped manifest headers have no such column; for example `training-data/decompose-to-solve/manifest/pattern-01.md` carries `folder | problem | pattern | template | type | category | split | paragraphs | answer | status | plan | problem | solution | explanation`. `manifestRowsOf`, `manifestRowValues`, and `expectedAnswersOf` in `training-data/dataset-manifest.mjs` read columns by header name and none of them reads a read-set column. So a registry-reading plan can be built and fingerprinted (its `circuit.getDefinition` call is part of the `entry.compute` text and is therefore already inside `planFingerprint`), but the dataset has no place to publish which definitions it observed, which is the fact the invalidation contract and the audit trail depend on.

## Why the 40-to-67-line jsEval bodies are the symptom

The symptom the container shape addresses is measured, not rhetorical. Across the 772 book compute bodies the line count is median 8, mean 10.2, p90 21, and maximum 67; ten bodies reach 40 lines or more, and the longest are the world-as-a-system meta-reasoning and navigation families (67, 65, 57, 55, 53 lines) and the scientific-reasoning forms (52 and 48), the bodies that mix map-scale geometry, clock arithmetic, and graph/navigation traversal. A concrete instance is `teacher/families/decompose-to-solve/pattern-09.mjs`: it parses thirteen separate fields from the statement and then runs a single long `COMPUTE` body that converts local units to standard units, rounds to tenths, computes the batch count, waves, parallel capacity, buffer time, cost, and a deadline verdict — state bookkeeping that the model must regenerate as free-form JavaScript inside one body. This is precisely the surface where the failures land: decompose-to-solve is the single largest execution-error book in `exp-013` (83 items), and 25 of those are the two named graph failures `ready.after is not iterable` and `the plan must complete every task`. These bodies hand-roll the maps, queues, adjacency structures, ledgers, and accumulating records that a container plan would instead declare once (`container`) and stage as patches (`containerAdd`/`containerUpsert`/`containerRemove`), reading the result through a pure derived view (`containerFilter`). A container shape moves that bookkeeping out of the model's one body and into trusted runtime state with a revision and an invalidation contract, so the class of list-and-iteration compile and execution errors is removed from the target text rather than re-generated on every sample.

## The plan, ordered by dependency

Each step depends on the one before it: the validator must admit the commands before a family can declare them (step 1), the builder must assemble what the validator admits before any circuit exists to execute (step 2), provenance must judge the circuit the builder produced before it is safe to accept families (step 3), and the manifest column is a write-side fact that the families and the verifier then publish and read (step 4). Steps 5 and 6 are consumers of the first four: the families cannot exist until 1-4 land, and the measurement arm cannot run until the families and the verifier do.

### Step 1 — the family validator accepts container commands as intermediate wires

Files: `teacher/procedural/index.mjs` (`validateProceduralFamily`).

Change: extend the intermediate-wire command whitelist to admit `container`, `containerAdd`, `containerUpsert`, `containerRemove`, and `containerFilter`, and add the body checks the commands' own contracts imply — a `container` wire's body must parse as a profile with a `kind` (reusing `parseProfile`, the same function `wires/standard/containers.mjs` uses), and a mutation wire's body must name a `target` while a filter's body must name a `source` and a non-empty `predicate`. The existing name rules (lowercase start, not `answer`/`slots`/`facts`, declared once) and the non-empty-body rule stay and now apply to container wires too. The five existing whitelisted commands are untouched, so no shipped family regresses.

Acceptance: `loadProceduralFamilies` (exercised by `teacher/pilot.mjs`) loads a family whose `wires` declare `container` plus `containerAdd`/`containerFilter` without throwing; a family whose `container` body lacks a `kind` or whose `containerAdd` body lacks a `target` is rejected with a named message; and the existing procedural sources still load with no error.

### Step 2 — buildProgram builds container plans

Files: `teacher/families/index.mjs` (`buildProgram`, `validateCase`), with the procedural load path in `teacher/procedural/index.mjs` as the consumer.

Change: give `buildProgram` an explicit container path on top of its generic intermediate-wire loop. Emit each container command's profile body verbatim and never through `answerBody` (which is for `jsEval` only, and already is skipped for non-`jsEval` commands — this step makes that an asserted contract rather than an accident). Order the emitted wires so a `container` declaration precedes the mutations and filters that name its `target`/`source`, so the runtime's epoch rule ("a wire that reads a container reads it in a later epoch than the wire that writes it") holds by construction. Extend `validateCase` to parse `buildProgram(entry, {})` and, for a family that declares any container wire, additionally execute the built circuit against a throwaway slots draw so a malformed container body is caught at load time, not at export. Note that `planFingerprint` already folds every `entry.wires` element in as `name \u0000 command \u0000 body`, so a container plan's fingerprint (and therefore deduplication, leakage checks, and holdout clustering) is covered with no change; this step only needs to verify that a container plan and the non-container plan of the same family fingerprint differently.

Acceptance: `buildProgram(entry, slots)` for a container family returns a circuit that `parseCircuit` accepts, that the runtime executes to the family's answer, and whose `planFingerprint(entry)` differs from the same family's non-container fingerprint; a family whose `containerAdd` names a target that no `container` declaration precedes fails `validateCase` with a named error.

### Step 3 — the provenance battery judges reactivity for container shapes

Files: `training-data/provenance.mjs` (`verifyProvenance`, `perturbedSlotBodies`, `withSlotsBody`).

Change: make the reactivity judgment container-aware without changing what it proves. Enforce the seeding discipline at the source of truth: a container plan must seed its containers from a `$slots` or `$facts` reference (a `containerAdd items: $slots.records`), never from a baked intermediate `literal`, so the `withSlotsBody` perturbation of the `slots` wire actually reaches the container contents; `verifyProvenance` should flag a container plan whose seed is a baked literal as non-reacting rather than letting it pass. Extend the `usesInputs` classification so it reads `$`-references from container profile bodies, reusing each container command's own `analyze().values` (which already reports the `target`/`items`/`source`/predicate references) instead of relying on the JavaScript-only `findValueReferences` scan. The answer wire stays deterministic `jsEval` and must be a pure function of the state its epoch observes, which is the DS008 rule the perturbation run already enforces.

Acceptance: a container family whose answer is a pure function of its seeded state reacts to at least one perturbation and is counted in `computed`; a container family whose answer reads only container contents that no perturbed value seeded is reported in the `invariant` list with `usesInputs: false`, exactly as DS008 requires; a container family whose seed is a baked literal is reported as non-reacting rather than passing.

### Step 4 — the manifest column for the structural read set

Files: the manifest writer in `teacher/` (the module that prints the header row of each `manifest/<unit>.md`) and `training-data/dataset-manifest.mjs` (`manifestRowsOf`, `manifestRowValues`, `expectedAnswersOf`).

Change: add a `structural read set` column (or a narrower `reads` column) to the manifest header, empty for every non-registry plan, and list the definition names a registry-reading plan's `jsEval` body observes through `circuit.getDefinition` and `circuit.listDefinitions`. Because the readers in `dataset-manifest.mjs` already resolve columns by header name rather than position, the new column is backward-compatible: existing manifests keep their columns and a new column appears only where a registry-reading family is written. The write side must derive the read set from the family's compute body (or the family must declare it explicitly), and the read side must expose it in `manifestRowValues`.

Acceptance: the manifest row of a registry-reading family records the definition names its body reads; `manifestRowsOf`/`manifestRowValues` return those names for that row and none for a plain `slots`-plus-`answer` row; `node training-data/verify.mjs` still verifies the whole tree with the extra column present.

### Step 5 — two or three minimal container families

Files: a new procedural family module under `teacher/procedural/` (for example `teacher/procedural/containers.mjs`), registered as a procedural source in `teacher/sources/index.mjs`, with its dataset directory under `training-data/<source-id>/` and its manifest rows carrying the new read-set column where applicable.

Change: author three families, one per shape, each with the full family contract (`sample`, `statement`, `parse`, `solve`, `render`, `explain`, plus `id`/`name`/`type`/`category`/`difficulty`) and a `wires` array that declares the container plan; `buildProgram` (step 2) assembles it and the provenance battery (step 3) judges it. Shape one builds a typed store in stages: a `container` declaration, then two or more `containerAdd` patches that seed the records from `$slots`, and an `answer` that reads the committed store. Shape two patches it: a `container` declaration and seed, then `containerUpsert` (and optionally `containerRemove`) that changes a keyed record under a declared merge policy, and an `answer` that reads the patched view. Shape three queries it: a `container` declaration and seed, then a `containerFilter` over the store (possibly a filter over a filter), and an `answer` that reads the derived view. Every `solve` is an independent oracle over the parsed slots, so each accepted instance is `constructed_verified`.

Acceptance: `node training-data/verify.mjs` reports `verify: OK` over the whole tree with all three families' instances reproduced (circuit answer equals oracle) and all three proven reactive to perturbed slots; every one of the three circuits carries a `container` declaration wire plus at least one mutation and at least one read of the container; the family-level split keeps one family held out of training while the other two are trained, per DS008's family-level splitting rule.

### Step 6 — the measurement arm

Files: no new code beyond steps 1-5 and the container families; the arm is a future experiment whose data is produced by the export and whose score lands in `evaluation/registry/exp-0NN-...`, with its slice and recipe recorded in `training/PLAN.md` and the chat profile naming the container shapes in its system prompt (the DS008/DS009 requirement for any shape change).

Change (decision, not implementation): the baseline is `exp-020-1.7b-qwen3-dv6`, the arm the dv6 stage (`training/environment/overnight-dv6.sh`) is rebuilding toward and launching as of this writing — it trains the book-shape families but no container shape, on the recipe 2 epochs, lr 1e-4, per-device batch 4 with gradient accumulation 8, gradient checkpointing, preservation-10, save-steps 150, base model qwen3-1.7b. The container arm adds the three families (two trained, one withheld whole) to that export and trains with the same recipe, so the only variable against the baseline is the container shapes. Which slice decides: the newly withheld container family is the primary instrument — it asks whether the model emits a container declaration, a mutation, and a filter on a family it never saw, which is the transfer the shape exists to teach; the frozen 225-item book-derived holdout is the regression yardstick and is not expected to move, because the books remain the vocabulary-boundary case measured in `exp-012`/`exp-013` (2 of 225 at best); the plan-unseen validation rows remain the second-level check. Which numbers decide: oracle match percent, runtime completion percent, and parse/graph validity (which must stay 100%) reported per slice — withheld container family, book-derived holdout, and procedural-arithmetic clusters — plus a per-wire emission check on the withheld family's completions (does the target contain a `container` declaration, at least one mutation, and a filter, as a fraction of completions). Decision rule: the arm is judged by whether the withheld container family moves off zero and the book holdout does not regress; a container shape that transfers is the success, not the aggregate.
